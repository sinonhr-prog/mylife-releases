# Правила выпуска

Статус: спецификация будущего процесса. Автоматизированной сборки, подписанного APK и проверенного обновлятора здесь пока нет.

## Разрешённые файлы

В Git: README.md, SECURITY.md, RELEASE_PROCESS.md, UPDATES_PLAN.md.

В Assets каждого готового выпуска: `mylife.apk`, `SHA256SUMS`, `update.json`. Дополнительно — описание изменений, статус stable/preview, проверенные API/ABI/устройства и ограничения. Не публиковать манифест обновления без соответствующего проверенного APK.

Не загружать исходные рабочие каталоги, ключи, настройки, базы, архивы, внутренние отчёты, личные снимки экрана, SDK и кеши.

## Контракт update.json, схема 1

Обязательные поля: `schemaVersion` (1), `applicationId` (`local.mylife`), `versionCode` (положительное целое), `versionName` (строка), `minSdk` (целое), `assetName` (`mylife.apk`), `sizeBytes` (положительное целое), `sha256` (64 hex-символа), `channel` (`stable` или `preview`).

Файл манифеста и APK берутся из одного release ID/tag. URL APK определяется по разрешённому asset этого релиза, а не произвольной ссылке из описания. После скачивания поля сверяются с APK. Черновики исключены. Stable не получает prerelease; preview требует явного выбора пользователя.

Начальный сетевой маршрут: GitHub Releases API выбранного репозитория → metadata/asset того же релиза → проверенный HTTPS redirect на CDN GitHub. Конкретный allowlist доменов должен быть подтверждён реальной загрузкой до реализации. Никаких токенов GitHub в APK. Версии сравниваются по versionCode, обновление на равную/старую версию не предлагается.

## Последовательность издателя

1. Зафиксировать версию исходников и возрастающий versionCode. Пройти применимые quality/security/migration gates; проверить реальное количество тестов.
2. Собрать release APK и подписать постоянным release-ключом вне публичного репозитория. Debug APK не использовать как release.
3. Проверить подпись, package ID, versionCode, minSdk, ABI, debug=false, итоговый manifest и сохранение запрета автоматического backup/переноса данных.
4. На синтетических данных проверить установку и обновление V1 → V2 на API 29 и реальном целевом телефоне. Не считать отсутствие устройства успешной проверкой.
5. Сформировать update.json и SHA256SUMS из конечного подписанного APK. Создать draft release, загрузить только разрешённые файлы, проверить комплектность и опубликовать в согласованном канале.
6. Скачать опубликованный APK, сверить SHA-256 и подпись, проверить API/ссылки/канал; затем сообщить ссылку пользователю.

Первый релиз публиковать только с уже включённым обновлятором. Если приложение ещё не принято для реальных данных, выпуск явно помечается тестовым и описывает ограничения. Не заменять файлы опубликованной версии: исправления выпускаются под новым тегом и большим versionCode.

Автоматизацию загрузки можно добавить отдельно. Публичные workflow и недоверенные pull request не должны получать закрытый ключ подписи. Для начала сборка/подпись локальные; публикация имеет минимальные права только на этот репозиторий.
