# План реализации

Версия 2, 16.10.2026. Основан на ответах владельца в [PRODUCT.md](PRODUCT.md). Этот документ — общий roadmap; его детализация для обоих агентов находится в [harness/PLAN.md](../harness/PLAN.md): 12 этапов H00–H11, 48 шагов и критерии закрытия. Подготовлен только проектный пакет этапа 0; H00 ещё не запускался выбранным исполнителем. Номера этапов не означают автоматическое разрешение начать реализацию.

## Результат

Личный Android APK: вещи с фотографиями и оценкой, категории мест, задачи, заметки, локальные напоминания и сейф. Отдельный PIN/отпечаток. Все рабочие данные локальны и зашифрованы. Ручная переносимая копия. Минималистичный интерфейс одной выбранной темы. Поддержка Android 10+ с проверкой Vivo X200 Pro mini.

## Очередность и оценка

Оценка одного опытного Android-разработчика, в рабочих днях; не обещание срока и не оценка скорости агента. Нижняя граница предполагает быстрые решения владельца и доступные устройства. Внешнее security review и ожидание устройства считаются отдельно.

| Этап | Результат | Оценка |
|---|---|---:|
| 0 | Требования, план, структура, 5 дизайнов | текущий пакет |
| 1 | Сборка и проверка совместимости библиотек | 3–5 дней |
| 2 | Защищённое ядро, PIN и биометрия | 6–10 |
| 3 | Хранилища, миграции, файлы, ранний backup round-trip | 5–8 |
| 4 | Главная, каталог и покупки с фото | 5–8 |
| 5 | Места, заметки и задачи | 5–7 |
| 6 | Напоминания и работа в фоне | 4–7 |
| 7 | Сейф и законченный интерфейс восстановления | 6–10 |
| 8 | Проверки, оптимизация, ревью, личная бета | 7–12 |
| 9 | Исправления беты и первый личный выпуск | 2–4 |

Итого: 43–71 рабочий день, ориентир 9–15 рабочих недель без внешнего ожидания; резерв 20–30% на OEM-поведение и криптографические интеграции. Полезная бета без настоящих паролей возможна после этапа 5. Сейф не ускорять за счёт отказа от проверки восстановления.

## Этап 0 — проектирование

Результаты: требования и журнал решений; архитектура; модель данных; security/backup спецификация уровня плана; проверяемые критерии; пять цветовых макетов; корневые и модульные инструкции. Владелец утвердил «Бумага / Фокус», дашборд и меню слева. Нерешённые вопросы отмечены явно, не скрыты в коде.

Готовность: документы связаны, направления зависимостей не противоречат друг другу, макеты открываются локально, данные демонстрационные. Это не проверка Android и не аудит безопасности.

## Этап 1 — bootstrap и технические прототипы

1. Проверить наличие Android Studio/SDK, JDK, USB debugging и эмулятора. Установки — только в рамках отдельно порученной реализации.
2. Подобрать актуальные стабильные совместимые версии AGP/Gradle/JDK/Kotlin/Compose/Room/SQLCipher. Записать их в version catalog и docs/toolchain.md, приложить источники совместимости.
3. Создать настоящий Gradle Wrapper с проверенной checksum, модули из ARCHITECTURE.md, базовую Compose Activity, AppContainer. minSdk=29; compile/target SDK выбрать по текущей стабильной платформе, не по году телефона.
4. Зафиксировать applicationId до первого реального выпуска; рабочий кандидат `local.mylife.app`. Настроить локальный debug и отдельную release подпись.
5. На синтетической БД проверить Room + SQLCipher: открытие, миграция, WAL, ошибочный ключ, 16 KB page size, arm64/эмулятор и выбранный нижний Android.
6. Выбрать библиотеку Argon2id и streaming AEAD: поддержка, лицензия, ABI, размер, сопровождение, известные уязвимости, тестовые векторы. Не изобретать криптографию ради отсутствующей зависимости.
7. Проверить Keystore/CryptoObject на API 29 и Vivo. Измерить KDF. Составить окончательный ADR формата ключей и архива.
8. Настроить lint, форматирование, unit/UI tests, dependency verification и локальные команды.

Gate: воспроизводимая чистая сборка, старт на API 29 и Vivo, технический round-trip шифрования, зафиксированные версии/лицензии. Если совместимость не подтверждена, сначала скорректировать стек; не продолжать поверх фиктивного шифрования.

## Этап 2 — защищённое ядро

1. SessionController: Locked/Unlocking/MainUnlocked/VaultUnlocked, тайм-ауты, lifecycle, отмена операций.
2. Device-bound ключи, обёртки PIN и биометрии, уникальные nonce/AAD, независимые scopes main/vault/files.
3. Онбординг PIN 8–12 цифр, повторный ввод, локальная задержка попыток, обработка неверного PIN без изменения данных.
4. Биометрия только через криптографическую операцию. Обработка отказа, отсутствия сенсора, смены отпечатков и инвалидации ключа.
5. Блокировка при фоне/выключении экрана; отсутствие секретов в saved state/recents; восстановление навигации после авторизации.
6. Атомарная смена PIN и переобёртка ключей. Экран «Нет доступа» с переходом к восстановлению, без скрытого bypass.
7. Политики manifest: без INTERNET, exported=false для непубличных компонентов, безопасные PendingIntent, системные backup rules.

Gate: отрицательные тесты PIN/nonce/tag, process death и background, невозможность открыть vault через main session, отсутствие открытых ключей на диске, ревью модели угроз. Пока только тестовые секреты.

## Этап 3 — данные и раннее восстановление

1. Room-схемы по DATA_MODEL.md, ключи/индексы, транзакции, миграции и schema export.
2. Типизированные репозитории, единые validation errors, даты/деньги/оценки без неоднозначности.
3. Импорт фото: валидация mime/размера/decode, уменьшение, очистка EXIF копии, шифрование оригинала и thumbnail, атомарное связывание с записью.
4. Удаление/архивирование, уборка orphan файлов, восстановление после нехватки места и сбоя.
5. Ранний export/import CLI или внутренний тестовый экран на синтетических данных: все типы, вложения, main/vault, новое устройство и новые ключи.
6. Snapshot и staging поколения, лимиты архива, безопасная отмена. Миграция старого архива и отклонение неизвестного будущего формата.

Gate: полный round-trip между чистыми установками, побайтовая/логическая проверка содержимого, неверная фраза и повреждение не затрагивают текущую базу. Все миграции сохраняют данные. Созданные тестовые файлы не содержат открытые личные данные.

## Этап 4 — интерфейс и покупки

1. Использовать утверждённые «Бумага / Фокус»; перенести токены в Compose, локальная типографика, компоненты полей, кнопок, списков и диалогов. Повторный выбор компоновки не нужен.
2. Выдвижное меню слева по ☰ со всеми категориями и настройками, без нижних вкладок. Проверить Back, закрытие снаружи, фокус, крупный шрифт и независимую прокрутку. При открытии меню из сейфа закрыть его сессию.
3. Покупки: список, поиск/фильтр, создание, редактирование, фото, ссылка как текст, оценка 1–10, избранное, архив.
4. Главная-дашборд: текущие дела, ближайшие напоминания, последние посещения по lastVisitedAt и последние добавленные записи по createdAt; сейф исключён. В этапе 4 подключить доступные источники, остальные подключать в этапах 5–6 без вымышленных runtime-данных. Проверить пустые блоки, ошибки, загрузку, отсутствие места и отказ доступа к фото.
5. Локальный поиск и пагинация. Никакой незаметной загрузки картинки по URL.

Gate: сценарий создать товар → перезапустить → найти → изменить фото/оценку → восстановить из архива. Проверка 320–430 dp, крупного шрифта, TalkBack и действий одной рукой.

## Этап 5 — остальные личные записи

1. Места: магазины/парки/кафе/рестораны; пользовательские категории; адрес вручную; избранное, статус и дата последнего посещения. Подключить блок недавних посещений дашборда.
2. Заметки: обычный текст, поиск, сохранение без потери черновика; секретные черновики не писать открыто.
3. Задачи: сроки, статус, приоритет, завершение/возврат; ссылка на место или покупку только через публичные контракты.
4. Общий каталог и поиск по незасекреченным типам; сейф исключён.
5. Удаление категории не удаляет её записи молча: предложить перенос/отмену. Типизированные коллекции вместо произвольного конструктора полей.

Gate: все категории работают в авиарежиме; смена/удаление связей сохраняет целостность; сценарии поворота экрана/process death. Личная бета возможна на несекретных тестовых данных.

## Этап 6 — напоминания

1. Экран самостоятельных напоминаний и подключение к задачам; разовые/день/неделя.
2. Outbox + scheduler проекция, идемпотентные сигналы и отмена при завершении/удалении задачи.
3. Разрешения уведомлений и, при необходимости, точных сигналов; различать «запланировано», «уведомления запрещены», «время приблизительное».
4. Перезапуск, смена часов/зоны, пропущенные сигналы, locked UI; работа без ключей основной БД в фоновой службе.
5. Реальная проверка Vivo ночью/при Doze и после перезапуска. Инструкция по ограничениям энергосбережения без обещания обойти ОС.

Gate: documented device matrix; нет дублей; удалённая/завершённая задача не сигналит; содержимое не видно на lock screen. Отказ пользователя в разрешениях не ломает остальные функции.

## Этап 7 — сейф и пользовательские копии

1. Повторный PIN/отпечаток; список сервисов, карточка, генератор CSPRNG, скрытие/показ пароля, ограниченное копирование.
2. Отдельный поиск, отсутствие экспорта plaintext, исключение из общего UI; корректное закрытие при навигации.
3. Настройки копий: создание архива, фраза/повтор, локальное/USB назначение, прогресс/отмена, проверка готовности файла.
4. Восстановление: предварительная проверка → предупреждение о замене → согласие → staging → переключение → подтверждение результата.
5. Локальное напоминание сделать копию; показывать дату последнего успешного экспорта, не утверждать что копия уже перенесена на компьютер.
6. Смена PIN, управление отпечатком, диагностика и понятное объяснение потери ключа/фразы.

Gate: реальное восстановление на другом чистом устройстве; отсутствие секрета в screenshot/recents/logcat/notifications/files; криптографическое ревью. Реальные пароли допускаются только после этого и финального security gate.

## Этап 8 — надёжность, скорость, проверка защиты

Выполнить TESTING.md полностью для release-кандидата: unit/instrumentation/UI/migrations/archive/manifest/dependencies. Прогнать 10 000 синтетических записей, ограниченную память, архив 1 ГБ, прерванный импорт и малый свободный диск. Проверить 16 KB native pages, разрешения, доступность и min API.

Снять Macrobenchmark на release build, добавить Baseline Profile при измеримом выигрыше. Проверить циклы зависимостей. Сопоставить применимые MASVS-контроли и доказательства; независимое ревью защиты ключей/архивов. Findings с риском потери/раскрытия данных блокируют выпуск, косметические замечания планируются отдельно.

Gate: нет критических/высоких проблем безопасности и потери данных; все обязательные проверки имеют свежий отчёт с версией/устройством/датой. Непроверенные OEM-копии обозначены, а не засчитаны.

## Этап 9 — личный выпуск

Собрать подписанный release APK, записать versionCode/versionName, SHA-256, список зависимостей, результаты gates и release notes. Перед обновлением сделать зашифрованную копию. Проверить обновление поверх предыдущей тестовой версии с сохранением БД. Провести 7–14 дней личной беты; исправить существенные ошибки. Настоящие данные не копировать в отчёт.

Ключ подписи хранится у владельца отдельно; потеря ключа требует отдельного сценария переустановки/восстановления. Откат APK после миграции БД обычно небезопасен: восстановление совместимой копии либо forward-fix, а не установка старой версии поверх изменённой схемы.

## После MVP

Отдельными проектными решениями: Autofill с проверкой доменов/подписей приложений; TOTP; чек-листы; дополнительные поля товаров; импорт из других менеджеров; локальный OCR; виджеты с безопасным содержимым. Каждый пункт проходит изменение модели угроз, формата архива, тестов и документации. Сервер/синхронизация в этот список автоматически не включаются.

## Как брать этап в работу

На входе: порученный номер этапа, прочитанные инструкции, состояние дерева и toolchain, критерии результата. На выходе: конкретные изменённые файлы, новые данные о совместимости, выполненные команды/проверки, ограничения, обновлённые STATUS/ERRORS. Изменение принятой границы защиты требует решения владельца; обычные обратимые детали реализации — самостоятельны.
