# ADR 0004: Потоковый архив v1 и восстановление после прерывания файловой операции

Статус: реализовано для synthetic проверки H10, профильное crypto/recovery review остаётся обязательным. 17.10.2026, run20261017-sol-h10-fixes.

## Причина

H10 обнаружил незашифрованные ZIP с ключами в cache и независимые замены main/vault/envelopes. Удаление временного файла в finally не защищает от смерти процесса.

## Решение

- Внешний формат .lifevault v1 сохранён: header/KDF/envelope и Tink AES-GCM-HKDF stream с теми же AAD. ZIP пишется прямо в шифрующий поток; inspect/restore читают его через проверяющий поток. Keys/manifest находятся в ограниченных memory buffers. На диск staging попадают только уже зашифрованные базы и вложения, не ZIP или raw keys.
- Проверяется весь поток до EOF, включая AEAD final segment после ZIP. Ввод ограничен по KDF, размеру sealed key, записям, общему decoded/ZIP объёму и manifest. Неизвестные/повторные пути отклоняются. Manifest и фактический набор/хэши файлов должны совпасть.
- Данные/обёртки меняются через RecoverableFileBatch: синхронизированные копии старых/новых зашифрованных файлов, журнал ready, замены по одному через atomic move, committed. До открытия storage при следующем запуске незавершённый журнал откатывается. Две envelopes PIN используют тот же протокол. Cleanup сначала атомарно выводит journal из активного имени, чтобы его прерывание не превратилось в ложный rollback.
- Перед export/restore обе DB-сессии закрываются. Непустой WAL блокирует export; snapshot открытой SQLite копированием не допускается. Restore включает удаления старых WAL/SHM/journal и отсутствующих в архиве вложений в тот же recoverable batch.
- Существующие 6-значные PIN по-прежнему принимаются при входе. Для создания/смены отклоняются очевидные одинаковые цифры и последовательности, как требует SECURITY. Счётчик ошибок PIN переживает повторное создание SessionManager.

## Проверки и ограничения

Synthetic тесты: сбой после первой замены, прерывание Error и запуск recovery новым экземпляром, late restore failure с сохранением обеих старых БД/ключей, interrupted PIN change и оба старых PIN-envelope, отсутствие промежуточного staging при streaming export, negative archive checks.

Это recoverable transaction, а не одновременная видимость нескольких файлов для независимых процессов. Контракт — один писатель, закрытые БД и recovery перед их открытием. Проверяется программная остановка процесса; durability при реальном обесточивании/поведении OEM-файловой системы и directory fsync требуют профильного review/device fault injection. До этого H10 не закрывать и реальные секреты не разрешать.

Не проводились destructive restore на Vivo, чтение существующих пользовательских баз или конвертация данных владельца. Новый архивный формат и свои криптографические алгоритмы не вводились.
