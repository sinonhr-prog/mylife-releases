# План обновлений «Моей жизни» через GitHub

Дата: 17.10.2026. Статус: план и публичные документы опубликованы. Android-обновлятор и выпуск APK не реализованы. Репозиторий: https://github.com/sinonhr-prog/mylife-releases, commit `6b730d5366252e347e4ed109c5c30d2a33ee1156`. Итог проверок — в STATUS и handoff текущего запуска.

## Цель и границы

Первый распространяемый APK уже содержит экран «Настройки → Обновления». Следующие версии скачиваются из публичного GitHub Releases и устанавливаются поверх приложения с подтверждением Android. Git используется для истории исходников; телефон получает готовый APK через HTTPS, без git-клиента.

Поручение владельца разрешает новый публичный репозиторий и встроенное обновление. Это узкое изменение прежней политики «без INTERNET», а не разрешение синхронизации, аналитики или передачи записей. Перед реализацией согласовать документы PRODUCT, SECURITY, ARCHITECTURE, TESTING, AGENTS и карточки harness с этим решением. Нельзя просто удалить проверку запрета сети: заменить её проверкой новой ограниченной политики.

## 1. Публичный канал

Создан новый public-репозиторий https://github.com/sinonhr-prog/mylife-releases. Существующий проект не публикуется целиком.

Allowlist начального commit: README.md (назначение, установка, обновление, статус безопасности), SECURITY.md (как сообщать об уязвимостях без секретов), RELEASE_PROCESS.md (правила выпуска), UPDATES_PLAN.md (обезличенный план). Локальные копии — docs/release-channel/. Для каждого релиза: mylife.apk, SHA256SUMS, update.json и описание изменений. Первую публикацию пометить тестовой, если остальная функциональность/защита ещё не принята; отдельный preview-канал явно включается пользователем, stable не должен получать prerelease.

Не включать исходники без отдельного решения, .git существующего проекта, внутренние отчёты, логи, screenshots, SDK, caches, local.properties, keystore, подписи ключами в виде секретов, пользовательские базы, архивы и настройки. Сертификат подписи APK публичен по природе; закрытый ключ остаётся отдельно.

## 2. Контракт релиза

update.json версии схемы 1: applicationId, versionCode (целое), versionName, minSdk, assetName, sizeBytes, sha256, channel. Привязать его к тому же release ID и tag, что и APK. Не брать произвольный URL из описания релиза. Проверять соответствие metadata самому APK.

Постоянные: владелец/репозиторий, applicationId, имя asset и доверенный сертификат подписи. versionCode строго растёт; сравнивать числа, а не строки versionName. Старые APK не заменять в опубликованных версиях. Для исправления выпускать новую версию.

Контрольная сумма выявляет повреждение, но сама по себе не защищает от захвата репозитория: update.json и APK доступны одному издателю. Доверие обеспечивают проверка криптографической подписи APK доверенным сертификатом и системная проверка Android. Первую установку пользователь получает из проверенного официального канала.

## 3. Подпись и сборка

До первого APK назначить постоянный release-ключ, владельца и резервную копию; ключ не передавать в чат, публичный Git или логи. Все будущие сборки подписывать тем же ключом. Проверять apksigner, applicationId, versionCode, ABI, minSdk, запрет debuggable и итоговый merged manifest. Debug и release остаются разными приложениями: переход с debug не считать обновлением с сохранением данных.

Сначала собирать и подписывать локально. Загрузку разрешённых файлов выполнять после проверок отдельной командой выпуска. Последующая автоматизация не должна давать публичному репозиторию или workflow от pull request доступ к ключу. Предпочтителен локальный издатель или отдельный закрытый контур сборки с минимальными правами; public-репозиторию достаточно готовых файлов. Автопубликация только в рамках явно разрешённой политики выпуска.

## 4. Обновлятор в первом APK

Экран: установленная версия, кнопка «Проверить обновления», новая версия и описание, «Скачать», прогресс, «Установить», отмена и понятные состояния ошибок. Начальный режим — проверка по кнопке. Не вводить постоянный polling/фоновые сервисы; автоматическую проверку при запуске предложить отдельной настройкой после первого рабочего среза.

UI → ViewModel → интерфейс репозитория обновлений → отдельный сетевой клиент. Клиент не получает DAO, ключи, PIN, записи, вложения или идентификатор устройства. Новый Gradle-модуль не обязателен: сначала отдельный пакет с проверяемой границей внутри существующей структуры.

Добавить INTERNET и REQUEST_INSTALL_PACKAGES. Запретить cleartext; HTTPS, системная TLS-проверка, ограничения времени/размера, потоковая запись в приватный временный cache, отмена и очистка. Сеть только для GitHub API и загрузки release assets; каждое перенаправление проверять по HTTPS и проверенному allowlist доменов, включая фактический CDN GitHub. Не разрешать произвольные *.githubusercontent.com без обоснования. Эту цепочку проверить на реальной загрузке до фиксации allowlist.

Android INTERNET действует на всё приложение: проверка доменов является ограничением архитектуры и кода, а не системной изоляцией по доменам. GitHub/CDN видит IP и технические параметры HTTP; не обещать полного отсутствия внешнего взаимодействия. Токен GitHub в APK не нужен и запрещён.

Release notes отображать как безопасный обычный текст; никакого HTML/WebView/исполнения кода. Не логировать временные CDN URL. Обработать 403/429, отсутствие релиза, плохие JSON, таймаут, отсутствие сети, нехватку места, несовместимую версию Android и повторные нажатия. Использовать кеш/backoff, не частые запросы.

До установки сверить размер, SHA-256, пакет, versionCode, совместимость и криптографическую подпись APK. Стратегию ротации сертификата отдельно проектировать с учётом signing lineage; в первой версии ключ не ротировать. Повреждённый/чужой APK удалить и не передавать установщику.

Использовать PackageInstaller с обязательной обработкой STATUS_PENDING_USER_ACTION и итогового результата. Проверить canRequestPackageInstalls и при необходимости открыть системную настройку для этого приложения. После разрешения/возврата из настроек восстановить состояние. Не обещать бесшумную установку. Отмена установки оставляет старую версию работоспособной. Чистить временные файлы после завершения/следующего запуска.

## 5. Данные и проверка

Обновление не удаляет приложение. Миграции Room/архива версионируются, destructive fallback запрещён; миграции и восстановление после сбоя проверять отдельно. Наличие одного ключа подписи само по себе не гарантирует сохранность данных.

Минимальная приёмка: собрать V1 и V2 с одним release applicationId/сертификатом; установить V1, создать синтетические записи, скачать V2 через встроенный экран и установить поверх; проверить версию, записи, lock/unlock, напоминания и миграции. Выполнить на API 29 и реальном Vivo. Отдельно проверить arm64 APK; x86_64 эмулятор не подтверждает работу ARM-библиотек.

Негативные проверки: неверная подпись/пакет/hash, понижение versionCode, недоверенный redirect/HTTP, prerelease в stable, несовместимый minSdk, усечённая загрузка, отмена/kill процесса, отказ в разрешении установки, offline/403/429, мало места. Проверить, что синтетическое содержимое записей отсутствует в запросах/логах и сеть прочих функций не используется. Полные обязательные security/release gates сохранить.

## Последовательность и готовность

1. Передача lock и подтверждение модели/маршрута; запись выявленных ограничений в базу знаний, исправление устаревшего статуса.
2. ADR о сетевом исключении и канале выпуска; синхронизация требований и harness без выдачи согласий от имени владельца.
3. Создание публичного репозитория, публикация только трёх проверенных документов; проверить URL и публичную видимость.
4. Настройка release-подписи и реализация обновлятора; статические/unit/интеграционные проверки.
5. Сквозная установка V1 → V2 с синтетическими данными на API 29 и Vivo.
6. Публикация первого APK только после применимых review/gates, с описанием реальных ограничений и SHA-256. Проверить скачанный опубликованный файл; затем выдать пользователю ссылку.

Готово, когда пользователь может скачать первый APK с GitHub, установить его и получить следующую подписанную версию через встроенный экран с сохранением синтетических данных. Сейчас опубликованы только четыре документа канала; APK и этот сценарий ещё не готовы.
