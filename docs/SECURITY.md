# Безопасность и восстановление

Статус: проектируемая модель, реализация не создана и аудит не выполнен. Нельзя обещать абсолютную защиту.

## Угрозы и границы

Защищаем записи на заблокированном телефоне, извлечённые файлы, случайный системный backup, утечки через журнал, скриншоты, кеши, уведомления, буфер и подмену архива. Отдельный сейф уменьшает случайное раскрытие при обычной работе.

Разблокированное заражённое/root-устройство, враждебная клавиатура/Accessibility, фото экрана другой камерой и скомпрометированная ОС находятся за пределами гарантируемой защиты. Программный лимит PIN нельзя считать аппаратной защитой от перебора. Биометрия не повышает стойкость слабого альтернативного PIN. Старый Android совместим функционально, но устройство без патчей безопасности имеет дополнительные риски.

## Ключи и PIN: кандидат для обязательного прототипа

Используются независимые случайные ключи для основной БД, сейфа и файлов; системный CSPRNG. AES-256-GCM с уникальным nonce и аутентифицированными version/purpose/id для обёрток и небольших объектов. SQLCipher управляет своим форматом страниц. Ключи не выводятся из имени устройства, не зашиваются в APK и не записываются в preferences.

PIN приложения: 6 цифр (утверждено владельцем 17.10.2026), запрет очевидных комбинаций (111111, 123456 и т.д.), повторный ввод. Отдельный случайный salt и Argon2id (64 MiB, t=3, p=1, ~1.3 с). В связи с энтропией 6 цифр (10⁶ комбинаций) защита от offline-перебора гарантируется обязательной аппаратной обёрткой Android Keystore: без ключа Keystore украденный файл базы не позволяет проверять PIN. На устройстве перебор блокируется нарастающей задержкой. Ручной архив .lifevault защищается отдельной длинной фразой высокой энтропии.

Обёртка ключа по PIN имеет две защиты: ключ, полученный из PIN через KDF, и неэкспортируемый device-bound ключ Android Keystore. Кандидат композиции — вложенные AEAD-обёртки с различными purpose/AAD. Порядок, формат, библиотека, параметры и crash-consistency фиксируются ADR после security review; не реализовывать по одному этому абзацу без спецификации и тестов. Без Keystore-фактора украденный файл не должен позволять проверять PIN. При полном захвате устройства атакующий потенциально сможет использовать Keystore как оракул: PIN остаётся слабее длинной фразы.

Биометрический путь — независимая обёртка того же ключа ключом Keystore, требующим успешной сильной биометрии через CryptoObject. Не хранить расшифрованный PIN ради отпечатка. Смена набора биометрии/инвалидация ключа отключает этот путь и предлагает PIN; не удаляет базу. Проверять фактический уровень защиты ключа; отсутствие StrongBox не должно приводить к молчаливому хранению ключа открытым текстом. Аппаратный TEE/StrongBox предпочтителен; неподтверждённый уровень показывать и не считать пройденным gate для реальных паролей.

Обычная сессия получает только ключи основного раздела. Ключ сейфа разворачивается отдельно после повторной авторизации; интерфейсы не позволяют main session читать vault. При блокировке закрыть БД, отменить запросы, убрать UI-состояния и ссылки на секреты, очистить доступные mutable buffers. Гарантированное стирание всех копий в JVM памяти не обещать. Не сохранять секреты через SavedStateHandle, rememberSaveable или navigation arguments.

Неверный PIN: локальная нарастающая задержка, например после 5 попыток 30 с, затем до 15 мин; счётчик переживает обычный перезапуск. Никакого автоматического уничтожения данных. Смена часов, переустановка и root показывают пределы такой защиты. Смена PIN требует текущего PIN или предусмотренной сильной авторизации и атомарно меняет обёртки; тест сбоя на каждом шаге обязателен. Если PIN забыт, но биометрия доступна, разрешать безопасную переустановку PIN только через отдельный подтверждённый сценарий. Иначе — восстановление из архива; секретного обхода нет.

## Хранение и отображение

- main.db и vault.db зашифрованы целиком; проверить WAL/SHM/journal, индексы, служебные файлы и аварийные сценарии.
- Вложения и thumbnail зашифрованы; импорт читается потоком; EXIF геолокацию удалять у импортированной копии. Исходный снимок в галерее/провайдере остаётся вне контроля приложения — шифрование копии его не удаляет.
- Photo Picker/локальный файловый выбор, без широкого доступа ко всей галерее. Облачные источники системного picker не гарантированно исключены самим отсутствием INTERNET: для строгого режима выбирать локальный провайдер/документ и явно тестировать ограничения.
- Все окна с личными данными защищены FLAG_SECURE; скрывать превью recent apps, содержимое уведомлений. Защита зависит от ОС и не перекрывает все способы захвата.
- Пароли скрыты до явного показа. Копирование только по нажатию, sensitive flag, попытка очистки через 30 с и при следующем входе, только если буфер всё ещё содержит нашу запись. Очистку после смерти процесса и на всех OEM гарантировать нельзя; это известный риск до внедрения Autofill.
- Не логировать PIN, ключи, SQL-параметры, названия, логины, URI, содержимое заметок или полный stack trace с PII. Диагностика — локальные код ошибки/версия/этап, без удалённой отправки.
- Строго ограниченный сетевой контур: единственное исключение — ручная проверка и загрузка обновлений приложения из официального публичного репозитория GitHub Releases. Личные данные, базы данных, пароли, ключи и файлы изолированы от сети на уровне архитектуры модулей. Никаких сторонних SDK, Firebase, аналитики, WebView или загрузки превью ссылок.

## Сетевая безопасность и канал обновлений

- **Разрешения**: `android.permission.INTERNET` и `android.permission.REQUEST_INSTALL_PACKAGES` используются исключительно клиентом обновлений (`updater`).
- **Сетевой профиль**: только HTTPS (TLS 1.2+); незашифрованный трафик (cleartext HTTP) запрещён конфигурацией `network_security_config.xml`.
- **Allowlist хостов**: клиент обновлений обращается только к API GitHub (`api.github.com`) и CDN релизов (`github.com`, `objects.githubusercontent.com`). Редиректы на сторонние домены блокируются.
- **Верификация APK**: до вызова установщика скачанный APK проверяется на соответствие хэшу SHA-256 из `update.json`, совпадение `applicationId`, увеличение `versionCode` и соответствие криптографического сертификата подписи доверенному сертификату разработчика (signing certificate pinning). Недоверенный или повреждённый APK немедленно удаляется из кэша.
- **Установка**: через системный `PackageInstaller` с обязательным подтверждением пользователем (`STATUS_PENDING_USER_ACTION`). Бесшумная установка без ведома пользователя невозможна и не проектируется.

## Системные копии

Отключить allowBackup; создать правила fullBackupContent для старых Android и dataExtractionRules для современных, исключая базы, файлы, shared preferences, device-protected области и любые поддержанные виды переноса. Одного allowBackup=false недостаточно для утверждения «нет D2D на всех устройствах». Проверять итоговый manifest и правила, затем реально проверять backup/restore/перенос на поддержанных версиях и Vivo. Ключи и данные не должны попасть в автоматические копии; отсутствие доступа к конкретному OEM-переносу отмечается как непроверенная часть.

## Ручной архив .lifevault

Только по явному действию, после авторизации обоих хранилищ. Парольная фраза отдельная от PIN, не хранится приложением. На экране объяснить: потеря телефона вместе с фразой/копией означает потерю данных; сервис восстановления отсутствует.

Версионированный формат: magic/version, ограниченные параметры KDF и salt, AEAD-обёртка нового случайного ключа архива, аутентифицированный manifest и зашифрованный поток записей/вложений. Использовать готовую проверенную streaming AEAD-библиотеку; выбрать её вместе с Argon2id в прототипе. Строковые поля, таблицы, размеры, число файлов, относительные имена, хэши и версии схем валидируются. Названия и содержимое доступны только после проверки защиты. Общий размер, наличие файла и часть заголовка скрыть невозможно.

Экспорт — согласованный снимок двух БД и вложений: временная блокировка изменений либо проверенный snapshot протокол. Не копировать произвольно открытую SQLite-базу без WAL. Писать зашифрованно в временный файл, финализировать только после успеха; отменённый/неполный экспорт не показывать как готовый. У внешнего DocumentsProvider атомарное переименование не гарантировано: проверять завершение и объяснять очистку неполного файла.

Системный выбор назначения способен показывать облачные провайдеры. Для строгого режима ограничить проверенными локальными/USB destinations; не обещать, что любой URI локальный. Архив не отправлять автоматически. На компьютере копировать уже зашифрованный файл.

Восстановление: проверить заголовок/лимиты → парольную фразу и AEAD → распаковать в новую приватную зашифрованную staging-область → проверить схемы/ссылки/файлы → создать новые локальные ключи, PIN и биометрические обёртки → атомарно переключить активное поколение хранилищ → пересоздать напоминания → удалить старое поколение после успешного открытия. При сбое до переключения рабочая база остаётся прежней. Защита от path traversal, decompression bomb, слишком больших KDF-параметров, подмены версии, обрезания и смешения архивов обязательна.

Старая копия сохраняет старые секреты даже после смены пароля в приложении. Удаление файла на flash не гарантирует физическое стирание; контролируем удаление ключей/ссылок и минимизацию следов. Потеря ключа подписи APK мешает обновлению установленного приложения: ключ подписи хранится отдельно от репозитория и резервируется владельцем.

## Обязательная контрольная точка

До ввода реальных паролей: утверждённая спецификация key envelopes/archive; тестовые векторы; API 29 и Vivo; отрицательные тесты; успешное восстановление на чистом устройстве; ревью специалистом криптографической части. Без этого результат называется прототипом и работает только на синтетических данных.
