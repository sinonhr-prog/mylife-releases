# Архитектура

## Выбор

Нативный Android на Kotlin + Compose. Он соответствует единственной целевой платформе и даёт прямую работу с Keystore, биометрией, локальными уведомлениями и жизненным циклом. Flutter/React Native не запрещены в принципе, но сейчас добавляют второй слой интеграции без подтверждённой потребности в iOS. PWA не выбираем для сейфа и надёжной фоновой работы.

Приложение — модульный монолит без backend. Поток данных однонаправленный: действие UI → ViewModel → интерфейс репозитория → локальное хранилище → Flow состояния → UI. Отдельные use-case классы вводить только для повторяемых или сложных операций (восстановление, смена PIN, завершение задачи с отменой сигнала).

## Модули и направление зависимостей

```text
app → core:model, core:security, core:storage, core:designsystem
core:storage → core:model, core:security
core:security → core:model
core:designsystem → Compose; без storage/security
core:model → Kotlin; без Android/Room/Compose
```

`app` — composition root: связывает реализации с интерфейсами через простой AppContainer. Hilt добавить только если ручная сборка зависимостей действительно станет сложной. Пакеты feature внутри app не импортируют внутренние классы друг друга. Общение — через интерфейсы и типизированные идентификаторы. Прямого доступа UI к DAO нет.

Пять Gradle-модулей достаточно для начала; каждый экран не становится отдельным модулем. Сначала границы пакетов, выделение feature-модуля при отдельном цикле развития/тестирования. Не создавать generic Entity/JSON вместо типизированных таблиц и правил.

## Стек и фиксация версий

- Kotlin; Compose + Material 3 с собственными токенами; ViewModel, StateFlow, Coroutines.
- Room поверх поддерживаемого `sqlcipher-android`; выбирать совместимую стабильную комбинацию в техническом прототипе, не копировать старую `android-database-sqlcipher`.
- Kotlin Serialization для версионированных моделей архива; JSON не хранится незашифрованным на диске.
- Android Keystore + AndroidX Biometric, стандартные AEAD-примитивы; библиотека Argon2id выбирается отдельным сравнением поддержки/лицензии/ABI и тестовыми векторами.
- AlarmManager для пользовательских напоминаний. WorkManager — только для отложенной сверки расписаний/очистки, без обещания точности времени.
- Ручная DI, локальные изображения через закрытый decrypting image loader; без сетевого image loader. DataStore — только несекретные настройки темы/онбординга.
- Gradle Kotlin DSL, version catalog, dependency verification/locking, ktlint, Android Lint, JUnit, Compose UI tests, Macrobenchmark.
- Конкретные версии Kotlin/AGP/Gradle/JDK/SDK закрепить вместе в этапе 1 после проверки официальной совместимости. Не ставить динамические `+`, не объявлять непроверенную комбинацию стабильной.

## Хранение

1. `main.db` — SQLCipher: покупки, места, задачи, заметки, категории, теги, напоминания.
2. `vault.db` — отдельный SQLCipher: записи сейфа. Другой случайный ключ и отдельная сессия; база закрыта вне сейфа.
3. `attachments/` — зашифрованные файлы и уменьшенные копии; случайные имена. Временные открытые копии на диске запрещены.
4. `key-envelopes/` — версионированные обёртки ключей, salt, параметры KDF; без ключей в открытом виде, без системного backup.
5. `scheduler` — минимальные UUID, время сигнала, правило повторения; отдельная защита Keystore для фонового доступа после первого разблокирования телефона. Никаких названий/текста. Это осознанное исключение из PIN-зависимой сессии: приложение должно показывать общий сигнал при заблокированном UI. ОС также знает время сигнала. Проверить и зафиксировать в security review.

Каждый файл и БД размещается в приватной области приложения, исключённой из системного копирования. Для больших файлов потоковая проверенная AEAD-конструкция; не изобретать собственный протокол блоков. Формат файла содержит версию, идентификатор ключа и аутентифицированные метаданные.

## Поиск и скорость

Главная — локальный DashboardRepository/read model: ограниченные выборки текущих задач, следующих напоминаний, посещённых мест и свежих записей. UI получает типизированные summary-модели, а не DAO/ключи. Даты посещения вводятся вручную; правила сортировки в DATA_MODEL.md. Ни общий поиск, ни дашборд не зависят от vault. Основная навигация — меню слева по ☰ со всеми категориями, без нижних вкладок. Тема «Бумага»; вариант расположения блоков выбирается до переноса макета в Compose.

Индексы по categoryId, updatedAt, dueAt/status; ключи UUID; пагинация. FTS для заметок и описаний внутри зашифрованной main.db, без отдельного открытого индекса. Поиск сейфа только внутри открытой vault.db. Изображения декодируются уменьшенными, кеш в памяти ограничен и очищается при блокировке. Записи и файлы не загружаются целиком в память.

Целевые показатели для release build на среднем телефоне 2020 года: холодный запуск до экрана входа p95 ≤ 1,5 с; поиск 10 000 записей p95 ≤ 200 мс после открытия БД; сохранение обычного текста p95 ≤ 150 мс; заметные зависания >100 мс отсутствуют в типовом скролле. KDF сознательно медленный и измеряется отдельно (ориентир 0,5–1,5 с). Это бюджеты для проверки, не уже достигнутые результаты.

## Напоминания

Основная БД хранит исходное правило; scheduler — минимальную проекцию для доставки. Запись/изменение задачи и outbox-события планирования — одна транзакция. Идемпотентный reconciler обновляет PendingIntent по стабильному reminderId; повторная доставка не создаёт дублей. Worker не получает ключи основной БД в заблокированной сессии: работает с готовой минимальной проекцией.

Обычные сигналы могут задерживаться в Doze. Если требуется точное время, запросить предусмотренный платформой доступ к exact alarms, только после объяснения, и реализовать честный fallback. На Android 13+ нужно разрешение уведомлений. После перезагрузки пересоздавать сигналы после первого разблокирования устройства; не обещать их до него. Отдельно тестировать смену часового пояса, перевод часов, летнее время, пропущенный сигнал, выключенный телефон и force-stop. Время повторяющихся личных напоминаний по умолчанию следует местному времени устройства; разовые сохраняют абсолютный instant. Прошедшие после перезагрузки объединять в один нейтральный сигнал, не воспроизводить десятки уведомлений.

Vivo может ограничивать фоновую работу. Показывать диагностику разрешений и понятную инструкцию настройки устройства; не отключать энергосбережение без согласия и не обещать гарантированную доставку при force-stop.

## Подсистема обновлений

Раздел «Настройки → Обновления» реализуется внутри пакета `local.mylife.app.feature.settings.updater`:
- `UpdateRepository` (интерфейс в доменном слое): проверка версии, статус загрузки, запуск установки.
- `GitHubReleaseClient`: легковесный HTTP-клиент поверх стандартного `HttpsURLConnection` с ограничением хостов (`api.github.com`, CDN релизов), чтением `update.json` и потоковой загрузкой APK в приватный кэш. Не зависит от DAO, баз данных, ключей или секретов.
- `ApkVerifier`: сверка размера, SHA-256, `applicationId`, возрастания `versionCode` и отпечатка сертификата подписи APK до передачи в установщик.
- `PackageInstallerHelper`: интеграция с Android `PackageInstaller`, обработка интента `ACTION_MANAGE_UNKNOWN_APP_SOURCES` и запуск системного диалога подтверждения обновления.

## Рост

Новый тип записей: спецификация → типизированная модель/репозиторий → миграция → UI-пакет → включение в каталог/поиск/архив → тесты → scoped README/AGENTS. Новая функция не получает доступ к сейфу автоматически. Кафе/парки/магазины расширяются данными категорий без копирования экранов.

Будущие iOS/синхронизация потребуют отдельного решения, модели угроз и миграции. Текущий план не обещает их бесплатное добавление. Для локального роста проверять 10 000 записей, 1 000 карточек с фото и архив 1 ГБ на синтетических данных; фактические безопасные лимиты определить замерами.
