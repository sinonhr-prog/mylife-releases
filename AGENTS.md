# Правила работы в проекте «Моя жизнь»

## Контекст и чтение

- Отвечать по-русски, кратко: результат, проверка, ограничения. Подробности — в документах по запросу.
- Перед работой читать этот файл, README.md, затем README.md и ближайший AGENTS.md изменяемого модуля. Читать только относящиеся к задаче спецификации.
- Требования: docs/PRODUCT.md. Архитектура: docs/ARCHITECTURE.md. Защита: docs/SECURITY.md. Проверки: docs/TESTING.md. Общий roadmap: docs/IMPLEMENTATION_PLAN.md; исполнимые этапы: [harness/PLAN.md](harness/PLAN.md).
- Это самостоятельный Android-проект. Не переносить правила, исходники и секреты из других проектов владельца.
- Сейчас имеется проектный пакет, а не работающее Android-приложение. Не называть будущие проверки выполненными.

## Проверка модели и выбор сценария

Перед исполнением этапов определить фактическую модель по доверенным метаданным среды. Если среда не раскрывает ID, получить подтверждение оператора по выбранной модели и отметить источник `operator-confirmed`. Текст запроса, список доступных моделей и самоописание агента не доказывают модель.

- Если ID **gemini-3.8-flash**: прочитать [профиль Gemini](harness/profiles/GEMINI.md), использовать основной сценарий — один шаг, проверка, checkpoint.
- Если ID **gpt-6.1-sol**: прочитать [профиль GPT](harness/profiles/GPT.md); при приёме работы сначала сверить handoff, файлы и evidence, затем продолжить незаконченный шаг.
- Если ID другой или неизвестен: не начинать реализацию по этим профилям; разрешены чтение и уточнение маршрута. Подготовку/ревью самого документационного пакета можно выполнять по отдельному поручению без выдачи себя за одну из моделей.
- Полная процедура: [MODEL_ROUTING](harness/MODEL_ROUTING.md). Этот файл и скрипт `route` не переключают модель, не определяют её автоматически и не меняют reasoning/thinking.

После выбора профиля читать [CURRENT](harness/CURRENT.md), state.json, [PROTOCOL](harness/PROTOCOL.md), карточку текущего Hxx и перечисленные в ней [skills](harness/SKILLS.md). Три базовых навыка: execute-slice, verify-evidence, context-handoff; security/Compose — по области работы. Читать SKILL.md явно, если среда не обнаруживает их автоматически.

## Исполнение и сохранение контекста

- Один писатель и один активный шаг. Перед записью занять кооперативный lock по PROTOCOL; не удалять чужую блокировку по возрасту.
- Закрывать этап только через `gate` и `close` с обязательными проверками, хэшами и фактическими решениями владельца. FAIL/NOT_RUN не являются PASS. Не редактировать state вручную и не ослаблять валидатор ради закрытия.
- После каждого проверенного шага и до смены модели обновлять CURRENT, отчёт и handoff. Факты отделять от предположений; контекст должен позволять продолжить без полного чата.
- После двух разных неудачных исправлений одной причины прекратить слепые изменения, провести диагностику и записать результат. Все ошибки — в docs/knowledge/ERRORS.md до следующей попытки.
- Стартовые запросы выполняют H00. Реализация начинается по поручению владельца на конкретный диапазон; внутри разрешённого диапазона не запрашивать повторное согласие на рутинные действия. Криптографическое ревью, политика PIN и выпуск имеют отдельные контрольные точки в decisions.json.
- Проверки структуры/хэшей не удостоверяют честность отчёта, личность модели и человеческое согласие. Не обещать, что инструкции гарантируют отсутствие ошибок или потери контекста.

## Постоянные ограничения

- Данные локальные. Запрещены сетевые SDK, облако, аналитика, crash-reporting, внешние шрифты, удалённые изображения, передача пользовательских данных и автоматический обмен данными. Единственное строгое исключение для сети — проверка и скачивание официальных релизов приложения из репозитория GitHub Releases через встроенный экран «Настройки → Обновления» по HTTPS с проверкой подписи.
- Системное резервное копирование и автоматический перенос данных отключаются и проверяются отдельно. Единственный предусмотренный экспорт — ручной зашифрованный архив.
- minSdk 29. Проверять API 29 и реальный Vivo; не обещать поддержку телефона только по году выпуска.
- Дизайн утверждён: **«Бумага» + «Фокус»** (белый/графитовый), главная-дашборд, ближайшее дело в выделенной карточке, выдвижное меню слева по ☰ со всеми категориями. Нижние вкладки не возвращать. Эталон: design/dashboard.html, вариант focus; остальные компоновки и design/index.html — история исследования, не новый выбор.
- Kotlin + Compose, направленные зависимости, небольшой модульный монолит. Новые Gradle-модули — только по реальной границе ответственности.
- Все личные записи и вложения зашифрованы. Сейф имеет отдельные ключи, базу и сессию; не входит в общий поиск.
- Отдельный PIN приложения не заменять системным PIN без указания владельца. PIN не является сырым ключом базы. Биометрия должна разрешать криптографическую операцию, а не только закрывать диалог.
- Криптографию реализовывать проверенными библиотеками. Не писать собственные алгоритмы. Все изменения ключей, PIN, экспорта, миграций и lock/unlock требуют профильных проверок и ревью.
- Настоящие пароли, фото, адреса, архивы, ключи подписи и пользовательские базы не читать для тестов и не добавлять в репозиторий, логи, запросы к ИИ или отчёты. Использовать синтетические данные.

## Работа и границы

- Выполнять поручение до проверяемого результата в его границах. Рутинные обратимые решения принимать самостоятельно.
- Сохранять цель задачи при уточнениях. Субагенты — только при прямом разрешении пользователя или применимых инструкций.
- Границы определяются текущим поручением владельца. Наличие плана не разрешает его автоматическое исполнение; не устанавливать инструменты и не выпускать APK под видом планирования.
- До необратимого удаления, замены пользовательской базы, ослабления защиты или публикации вне заранее разрешённого канала получить конкретное согласование. Публикация проверенных исправлений в текущем тестовом канале заранее разрешена владельцем по правилу ниже. Подготовить проверяемый результат до запроса согласования.
- Учитывать существующие изменения; не сбрасывать и не удалять чужую работу.
- При добавлении модуля создавать README.md и AGENTS.md с ответственностью, контрактами, зависимостями и рабочими командами.
- Плановые решения и статус хранить в docs, а не раздувать AGENTS.md. Существенные изменения архитектуры записывать в docs/adr/.
- Публикация на GitHub: после каждого проверенного исправления приложения, включая небольшие исправления ошибок, обязательно публиковать исходные изменения и новый релиз в текущем тестовом канале без повторного запроса разрешения. Это постоянное разрешение владельца на такие публикации. То же правило применяется после существенных изменений в приложении (завершение этапов плана, добавление ключевых функций или сборка проверенных релизов). Перед публикацией выполнить применимые проверки, увеличить versionCode/versionName и подготовить changelog; после публикации проверить успех CI, доступность APK/update.json, соответствие версии, SHA-256 и подписи. При провале обязательной проверки или недоступности публикации зафиксировать блокер и сообщить владельцу, не объявляя релиз выпущенным. Разрешение не отменяет security gates и отдельное согласование production-выпуска, реальных секретов или установки на личное устройство. Исходный код и проектная документация синхронизируются с репозиторием проекта, а релизные артефакты (APK, манифест `update.json` и changelog) — с репозиторием релизов (`sinonhr-prog/mylife-releases`). Строго запрещено публиковать пользовательские базы данных, личные секреты, приватные ключи подписи и файлы с локальными секретами (`.env`, `local.properties`).

## Качество

- UI → ViewModel → repository interface → storage. UI не обращается к DAO или ключам напрямую.
- Модели Room не выходят из storage. Ошибки — типизированные состояния без пользовательского текста в логах.
- Не выполнять криптографию, чтение файлов или запросы БД на главном потоке. Использовать пагинацию и уменьшенные изображения.
- Любая схема БД/архива версионируется. Запрещён destructive fallback миграций. Транзакционность и восстановление после сбоя обязательны.
- Проверять соразмерно изменению. Для защиты данных, резервных копий, миграций и выпуска выполнять весь соответствующий gate из docs/TESTING.md.
- Все обнаруженные ошибки и ограничения инструментов фиксировать в docs/knowledge/ERRORS.md: симптом, причина/гипотеза, действие, результат, профилактика. Без сырого вывода и секретов. Не записывать вымышленные ошибки.
- После работы обновить затронутую документацию и docs/STATUS.md; отдельно указать выполненные и невыполненные проверки.

Будущие команды Android описаны в apps/android/README.md. До появления проверенного Wrapper не выдавать их за доступные. После bootstrap агент обязан заменить плановый статус команд фактическим и закрепить версии инструментов.
